# 🚀 测试架构重构 PRD：迁移至 Test Fixtures

## 1. 目标 (Objective)

将所有集成测试文件 (`tests/**/*.test.ts`) 从手动管理资源（Redis 连接、命名空间、清理逻辑）迁移到基于 Vitest Fixtures 的自动化测试架构 (`tests/helpers/suite.ts`)。

旨在实现：

- **彻底隔离**：每个测试用例拥有独立的 UUID 命名空间，支持并行执行。
- **消除样板代码**：删除重复的 `beforeAll`, `afterAll`, `createRedis` 和手动清理代码。
- **提高稳定性**：防止因键名冲突 (`Date.now()`) 导致的测试间歇性失败。

## 2. 涉及文件 (Scope)

所有位于 `tests/` 目录下的 `.test.ts` 文件，包括但不限于：

- `tests/concurrency/**/*.test.ts`
- `tests/core/**/*.test.ts`
- `tests/features/**/*.test.ts`
- `tests/resilience/**/*.test.ts`

## 3. 重构规则 (Refactoring Rules)

### 3.1 引入变更 (Imports)

- **删除**：`import { describe, it, expect, beforeAll, afterAll } from 'vitest'` (如果仅用于测试结构)。
- **删除**：`import { createRedis } from '../helpers/redis'` (除非测试需要显式创建额外的独立连接)。
- **新增**：从 suite 引入 `test` 和 `expect`。
  ```typescript
  // 根据文件深度调整路径，例如 ../../helpers/suite
  import { test, expect } from '../helpers/suite'
  ```

### 3.2 结构变更 (Structure)

- 将 `it('name', async () => { ... })` 替换为 `test('name', async ({ queue, redis, namespace }) => { ... })`。
- **删除** 文件顶级的 `namespace` 变量定义（如 `const namespace = ...`）。
- **删除** `beforeAll` 和 `afterAll` 中用于 Redis 连接和数据清理的代码块。

### 3.3 资源使用 (Resource Usage)

#### 场景 A：使用默认队列配置

如果测试只使用标准队列配置，直接使用解构出的 `queue` 对象。

**Before:**

```typescript
const queue = new Queue({ redis, namespace });
await queue.add(...);
```

**After:**

```typescript
test('case name', async ({ queue }) => {
  await queue.add(...);
});
```

#### 场景 B：使用自定义队列配置 (如 autoBatch, orderingDelayMs)

如果测试需要特定的队列参数，使用解构出的 `redis` 和 `namespace` 创建新实例。**必须使用注入的 `namespace`** 以确保隔离。

**Before:**

```typescript
const queue = new Queue({
  redis,
  namespace: `test:${Date.now()}`,
  autoBatch: true,
})
```

**After:**

```typescript
test('case name', async ({ redis, namespace }) => {
  // 注意：无需手动清理，Fixture 会在测试结束时清理该 namespace 下的所有 key
  const queue = new Queue({
    redis,
    namespace,
    autoBatch: true,
  })
  // ...
  // 如果创建了局部 queue，建议在 try...finally 或测试末尾调用 queue.close()，
  // 虽然 Redis 连接最终会被 Fixture 关闭，但显式关闭是好习惯。
})
```

### 3.4 Worker 处理 (Worker Handling)

- Worker 仍然需要手动实例化。
- 强烈建议使用 `try...finally` 块确保 `worker.close()` 被执行，防止 Worker 在测试失败后继续运行导致资源泄露。

**Pattern:**

```typescript
test('worker logic', async ({ queue }) => {
  const worker = new Worker({ queue, ... });
  try {
    worker.run();
    // 断言逻辑...
  } finally {
    await worker.close();
  }
});
```

## 4. 示例对照 (Examples)

### 示例 1：简单 CRUD 测试

**🔴 Old:**

```typescript
import { describe, it, expect, afterAll } from 'vitest'
import { Queue } from '../../src'
import { createRedis } from '../helpers/redis'

describe('Basic', () => {
  const redis = createRedis()
  const namespace = `test:${Date.now()}`

  afterAll(async () => {
    await redis.flushall()
    await redis.quit()
  })

  it('adds job', async () => {
    const q = new Queue({ redis, namespace })
    await q.add({ groupId: 'g1', data: {} })
    // ...
    await q.close()
  })
})
```

**🟢 New:**

```typescript
import { describe } from 'vitest'
import { test, expect } from '../../helpers/suite' // 路径需根据实际调整
import { Queue } from '../../src'

describe('Basic', () => {
  // 不再需要 beforeAll/afterAll 处理 Redis

  test('adds job', async ({ queue }) => {
    // queue 已经自动初始化并绑定了独立 namespace
    await queue.add({ groupId: 'g1', data: {} })
    // ...
    // 不强制手动 close，Fixture 会处理，但手动 close 也没问题
  })
})
```

### 示例 2：自定义配置与 Worker

**🔴 Old:**

```typescript
it('handles batching', async () => {
  const q = new Queue({ redis, namespace, autoBatch: true });
  const w = new Worker({ queue: q, ... });
  // ...
});
```

**🟢 New:**

```typescript
test('handles batching', async ({ redis, namespace }) => {
  // 使用注入的 namespace 和 redis 创建特定配置的 Queue
  const q = new Queue({
    redis,
    namespace,
    autoBatch: true
  });

  const w = new Worker({ queue: q, ... });

  try {
    w.run();
    // 测试逻辑
  } finally {
    await w.close();
    await q.close();
  }
});
```
