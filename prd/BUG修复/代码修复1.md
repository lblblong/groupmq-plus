# 修复实施 PRD：引入 Watchdog 机制修复群组状态丢失问题

## 文档概述
**目标**：解决 `reserveBlocking` 过程中因进程崩溃导致的 Redis 群组 ID 丢失（处于既不在 `ready` 也不在 `limited` 集合的“隐身”状态）问题。
**方案**：引入“看门狗（Watchdog）”机制，通过一个新的 Lua 脚本复用现有的群组状态刷新逻辑，定期扫描并自动修复所有群组的状态。

---

## 任务一：实现群组修复 Lua 脚本

### 1. 问题定义
当前系统缺乏全量扫描和修复群组状态的原子机制。如果 Worker 在 `BZPOPMIN` 之后崩溃，取出的 `groupId` 将丢失，导致该群组内的任务永久饥饿。

### 2. 潜在风险
*   **数据一致性**：Redis 集合状态与实际任务负载不一致。
*   **任务饥饿**：部分群组即使有任务也无法被调度。

### 3. 修复策略
创建一个新的 Lua 入口脚本，遍历 `ns:groups` 集合，并对每个群组调用现有的 `refreshGroupState` 模块。该模块具有幂等性，会自动处理清理、入队 Ready 或入队 Limited 的逻辑。

### 4. 技术实施细节

*   **涉及文件**：
    *   新建文件：`lua/repair-groups.lua`

*   **逻辑变更点**：
    *   文件位置必须在 `lua/` 根目录，以便 Loader 加载。
    *   代码逻辑如下（伪代码）：
        ```lua
        --- @include "includes/group-lifecycle/refresh-group-state"
        
        -- KEYS[1]: 命名空间 (ns)
        -- 获取所有群组: SMEMBERS {ns}:groups
        -- 遍历群组:
        --    调用 refreshGroupState({ ns=ns, groupId=gid, readyKey=..., limitedKey=... })
        -- 返回: 扫描的群组总数
        ```
    *   **关键点**：必须使用 `--- @include` 引用 `includes/group-lifecycle/refresh-group-state`，确保逻辑与主流程完全一致。

*   **交付标准**：
    *   脚本能被 TypeScript Loader 正确解析。
    *   脚本执行时无语法错误，并返回整数（群组总数）。

---

## 任务二：更新 Queue 接口与 Loader 定义

### 1. 问题定义
TypeScript 层缺少调用新 Lua 脚本的类型定义和封装方法。

### 2. 潜在风险
*   **运行时错误**：如果未注册脚本名，Loader 会抛出异常。
*   **调用困难**：没有封装的方法，Worker 需要手动构建 `evalScript` 调用。

### 3. 修复策略
在 `loader.ts` 中注册脚本名称，并在 `queue.ts` 中暴露 `repairGroups` 方法。

### 4. 技术实施细节

*   **涉及文件**：
    *   `lua/loader.ts`
    *   `queue.ts`

*   **逻辑变更点**：
    1.  **修改 `lua/loader.ts`**：
        *   在 `ScriptName` 类型定义中追加字符串字面量 `'repair-groups'`。
    2.  **修改 `queue.ts`**：
        *   在 `Queue` 类中新增方法 `repairGroups(): Promise<number>`。
        *   实现逻辑：调用 `evalScript(this.r, 'repair-groups', [this.ns], 1)`。
        *   增加日志：如果返回值大于 0，记录 info 级别日志（e.g., "Maintenance: Scanned and repaired states for N groups"）。
        *   异常处理：捕获所有错误并记录 error 日志，返回 0（不抛出异常）。

*   **交付标准**：
    *   `Queue` 实例可以成功调用 `repairGroups()` 方法。
    *   TypeScript 编译通过，无类型错误。

## 任务三：集成 Worker 定时维护（Watchdog）

### 1. 问题定义
虽然修复能力已具备，但 Worker 尚不会自动触发该逻辑。

### 2. 潜在风险
*   **被动响应**：系统无法自动从故障中恢复，必须等待人工干预。

### 3. 修复策略
在 `Worker` 中集成定时器，周期性调用 `queue.repairGroups()`。

### 4. 技术实施细节

*   **涉及文件**：
    *   `worker.ts`

*   **逻辑变更点**：
    1.  **修改 `WorkerOptions` 类型**：
        *   新增可选字段 `maintenanceIntervalMs?: number`。
        *   默认值注释说明：推荐 `60000` (1分钟)。
    2.  **修改 `Worker` 类**：
        *   新增私有属性 `maintenanceTimer?: NodeJS.Timeout`。
        *   新增私有属性 `maintenanceIntervalMs: number`。
        *   **构造函数**：初始化配置，默认值为 60000 ms。
        *   **新增方法 `startMaintenance()`**：
            *   校验 `maintenanceIntervalMs > 0`。
            *   计算 **Jitter（抖动）**：生成 `0` 到 `interval * 0.1` 之间的随机数，加到基础间隔上，防止多个 Worker 同时发起 Redis 扫描造成惊群效应。
            *   使用 `setInterval` 定期调用 `this.q.repairGroups()`。
            *   在回调中捕获并记录所有错误，防止 crash。
        *   **修改 `_runLoop` 方法**：
            *   在循环开始前调用 `this.startMaintenance()`。
        *   **修改 `close` 方法**：
            *   清理 `maintenanceTimer`。

*   **交付标准**：
    *   Worker 启动后，应按照配置的间隔定期执行 Lua 脚本。
    *   Worker 关闭时，定时器应被正确清除。
    *   多个 Worker 实例的执行时间点应有随机偏差（Jitter）。

---

## 全局注意事项

1.  **路径一致性**：请严格遵守 `lua/` 根目录存放入口脚本，`lua/includes/` 存放复用模块的规则。
2.  **幂等性**：`refreshGroupState` 本身是幂等的（多次执行结果相同），因此 Watchdog 可以安全地重复运行。
3.  **性能考量**：虽然 `repair-groups` 涉及全量 `SMEMBERS` 扫描，但在常规业务规模（< 10万群组）下，每分钟执行一次对 Redis 性能影响极小。Jitter 机制进一步确保了安全性。
