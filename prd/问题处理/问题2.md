# GroupMQ 自愈能力升级实施方案

## 1. 变更背景与目的

### 当前问题
当前系统假设 Redis 数据具有绝对的一致性。如果开发者或运维人员在 Redis 中手动执行了删除操作（例如：删除了 `job hash` 或 `group list`，但忘记清理 `delayed`、`ready` 等集合中的引用），系统会产生以下严重后果：
1.  **无限循环**：Promoter 会不断尝试获取已不存在的任务，导致 CPU 飙升。
2.  **死锁**：群组被物理删除后，Worker 仍尝试调度该群组，导致死循环。
3.  **资源泄漏**：失效的任务 ID 永久占据 ZSET 位置，阻碍后续任务执行。

### 解决方案
引入**“自愈机制 (Self-Healing)”**。我们将创建两个通用的 Lua 模块，用于在操作前校验数据的完整性。如果发现数据缺失（“幽灵数据”），系统将**自动清理**脏数据，确保流程继续运行。

---

## 2. 实施步骤概览

1.  **创建通用模块**：新建 `validate-job-integrity.lua` 和 `validate-group-integrity.lua`。
2.  **应用任务自愈**：修改延迟任务晋升、暂存任务晋升、死锁任务恢复脚本。
3.  **应用群组自愈**：修改群组状态更新脚本。
4.  **更新文档**：更新 Lua README。

### 步骤 1：创建通用校验模块

#### 1.1 新建文件 `lua/includes/common/validate-job-integrity.lua`

**功能**：检查任务 Hash 是否存在，若不存在则从指定的引用集合中移除 ID。

```lua
--[[
  验证任务完整性 (Validate Job Integrity)
  
  检查任务 Hash 是否存在。如果不存在（被手动误删），
  则从引用的集合（如 delayed, staged 等）中移除该 ID，实现自愈。

  Parameters:
    opts.ns: 命名空间
    opts.jobId: 任务 ID
    opts.refKey: (可选) 当前所在的集合 Key (如 delayedKey)，用于清理脏数据
    
  Returns: 
    true: 任务存在，数据完整
    false: 任务缺失，已执行清理
]]

local function validateJobIntegrity(opts)
  local ns = opts.ns
  local jobId = opts.jobId
  local refKey = opts.refKey

  local jobKey = ns .. ":job:" .. jobId

  if redis.call("EXISTS", jobKey) == 0 then
    -- 任务 Hash 不存在，执行清理
    if refKey then
      redis.call("ZREM", refKey, jobId)
    end
    return false
  end

  return true
end
```

#### 1.2 新建文件 `lua/includes/common/validate-group-integrity.lua`

**功能**：检查群组是否有效，若无效（空或被删）则从调度队列移除，防止 Worker 空转。

```lua
--[[
  验证群组完整性 (Validate Group Integrity)
  
  检查群组是否为空或被物理删除。
  如果是，则从 Ready/Limited 全局队列中清理，防止死循环。
  如果有效，顺便返回头部任务的分数（为了性能优化，避免重复查询）。

  Parameters:
    opts.ns: 命名空间
    opts.groupId: 群组 ID
    opts.readyKey: Ready 队列 Key
    opts.limitedKey: Limited 队列 Key
    
  Returns: 
    number: 群组有效，返回头部任务 Score
    nil: 群组无效（空或不存在），已执行清理
]]

local function validateGroupIntegrity(opts)
  local ns = opts.ns
  local groupId = opts.groupId
  local readyKey = opts.readyKey
  local limitedKey = opts.limitedKey

  local gZ = ns .. ":g:" .. groupId
  
  -- 获取群组头部信息
  local head = redis.call("ZRANGE", gZ, 0, 0, "WITHSCORES")
  
  if not head or #head < 2 then
    -- 群组为空或不存在，清理全局状态
    redis.call("ZREM", readyKey, groupId)
    redis.call("ZREM", limitedKey, groupId)
    return nil
  end

  -- 返回头部 Score，供后续逻辑使用
  return tonumber(head[2])
end
```

### 步骤 2：在核心脚本中集成任务自愈

#### 2.1 修改 `lua/includes/delayed-handling/promote-delayed-job-complete.lua`

**修改点**：引入新模块，替换原有的简单 EXISTS 检查。

```lua
--- @include "includes/group-lifecycle/update-group-ready-limited-state"
--- @include "includes/concurrency-control/is-group-at-capacity"
--- @include "includes/common/validate-job-integrity"

--[[
  将延迟任务晋升到等待队列 (Promote Delayed Job to Waiting)
  
  @param options table 参数对象
    - ns: string 命名空间
    - jobId: string 任务ID
    - delayedKey: string 延迟集合的 Redis key
    - readyKey: string 就绪集合的 Redis key
    - limitedKey: string 限流集合的 Redis key
  
  @return string "not-found" | "invalid-data" | "promoted"
]]

local function promoteDelayedJobToWaiting(options)
  -- 参数解构
  local ns = options.ns
  local jobId = options.jobId
  local delayedKey = options.delayedKey
  local readyKey = options.readyKey
  local limitedKey = options.limitedKey

  local jobKey = ns .. ":job:" .. jobId

  -- [FIX] 使用通用模块检查并自愈
  local isValid = validateJobIntegrity({
    ns = ns,
    jobId = jobId,
    refKey = delayedKey
  })

  if not isValid then
    return "not-found" -- 此时 delayedKey 中的脏数据已被清理
  end

  -- 从延迟集合移除
  redis.call("ZREM", delayedKey, jobId)

  -- 获取群组和分数
  local groupId = redis.call("HGET", jobKey, "groupId")
  local score = tonumber(redis.call("HGET", jobKey, "score"))

  if not groupId or not score then return "invalid-data" end

  -- 标记为等待状态
  redis.call("HSET", jobKey, "status", "waiting")
  redis.call("HDEL", jobKey, "runAt", "delayUntil")

  -- 加入群组等待集合
  local gZ = ns .. ":g:" .. groupId
  redis.call("ZADD", gZ, score, jobId)
  redis.call("SADD", ns .. ":groups", groupId)

  -- 更新群组状态（ready 或 limited）
  -- 这里的 updateGroupReadyLimitedState 内部也会使用新的群组校验逻辑
  updateGroupReadyLimitedState({ ns = ns, groupId = groupId, readyKey = readyKey, limitedKey = limitedKey })

  return "promoted"
end
```

#### 2.2 修改 `lua/promote-staged.lua`

**修改点**：在循环处理暂存任务时，增加对任务有效性的校验。

```lua
--- @include "includes/group-lifecycle/update-group-ready-limited-state"
--- @include "includes/common/validate-job-integrity"

-- Promote staged jobs that are now ready to be processed
-- argv: ns, now, limit
local ns = KEYS[1]
local now = tonumber(ARGV[1])
local limit = tonumber(ARGV[2]) or 100

local stageKey = ns .. ":stage"
local readyKey = ns .. ":ready"
local limitedKey = ns .. ":limited"
local timerKey = ns .. ":stage:timer"

local promotedCount = 0

-- Get jobs that are ready (score <= now)
local readyJobs = redis.call("ZRANGEBYSCORE", stageKey, 0, now, "LIMIT", 0, limit)

for i = 1, #readyJobs do
  local jobId = readyJobs[i]
  
  -- [FIX] 使用通用模块检查并自愈
  local isValid = validateJobIntegrity({
    ns = ns,
    jobId = jobId,
    refKey = stageKey -- 如果 Hash 没了，从 stageKey 移除
  })

  if isValid then
    local jobKey = ns .. ":job:" .. jobId
    local jobData = redis.call("HMGET", jobKey, "groupId", "score", "status")
    local groupId = jobData[1]
    local score = jobData[2]
    local status = jobData[3]

    if groupId and score and status == "staged" then
      local gZ = ns .. ":g:" .. groupId

      -- Remove from staging set
      redis.call("ZREM", stageKey, jobId)

      -- Add to group ZSET with original score
      redis.call("ZADD", gZ, tonumber(score), jobId)
      redis.call("SADD", ns .. ":groups", groupId)

      -- Update job status from "staged" to "waiting"
      redis.call("HSET", jobKey, "status", "waiting")

      -- Update group ready/limited state using centralized module
      updateGroupReadyLimitedState({ ns = ns, groupId = groupId, readyKey = readyKey, limitedKey = limitedKey })

      promotedCount = promotedCount + 1
    end
  end
end

-- Recompute timer: set to the next earliest staged job
local nextHead = redis.call("ZRANGE", stageKey, 0, 0, "WITHSCORES")
if nextHead and #nextHead >= 2 then
  local nextReleaseAt = tonumber(nextHead[2])
  local ttlMs = math.max(1, nextReleaseAt - now)
  redis.call("SET", timerKey, "1", "PX", ttlMs)
else
  redis.call("DEL", timerKey)
end

return promotedCount
```

#### 2.3 修改 `lua/includes/stalled-recovery/recover-stalled-jobs-complete.lua`

**修改点**：当锁过期且任务 Hash 也丢失时，强制清理 Processing 集合和 Key。

```lua
--- @include "includes/concurrency-control/is-group-at-capacity"
--- @include "includes/group-lifecycle/update-group-ready-limited-state"
--- @include "includes/lock/check-lock"
--- @include "includes/lock/release-lock"
--- @include "includes/flow/update-parent-flow"
--- @include "includes/common/validate-job-integrity"

-- 入参: opts.ns, opts.now, opts.gracePeriod, opts.maxStalledCount, opts.maxJobsPerScan
-- 功能: 查询过期任务，恢复或失败处理
-- 返回: 处理结果数组 [jobId, groupId, action, ...]

local function recoverStalledJobsCompletely(opts)
  local ns = opts.ns
  local now = opts.now
  -- ... 其他变量初始化保持不变 ...
  local gracePeriod = opts.gracePeriod
  local maxStalledCount = opts.maxStalledCount
  local maxJobsPerScan = opts.maxJobsPerScan or 500
  local processingKey = ns .. ":processing"
  local groupsKey = ns .. ":groups"
  local readyKey = opts.readyKey or (ns .. ":ready")
  local limitedKey = opts.limitedKey or (ns .. ":limited")

  local processingJobs = redis.call("ZRANGE", processingKey, 0, maxJobsPerScan - 1)
  local results = {}

  for _, jobId in ipairs(processingJobs) do
    local lockExists = checkLock({ ns = ns, jobId = jobId })
    
    if lockExists == 0 then
      -- 锁已过期，先检查任务是否存在（自愈逻辑）
      -- [FIX] 使用通用模块检查并自愈 ZSET
      local isValid = validateJobIntegrity({
        ns = ns,
        jobId = jobId,
        refKey = processingKey
      })

      if not isValid then
        -- [FIX] 补充清理 Processing 专用字符串 Key
        redis.call("DEL", ns .. ":processing:" .. jobId)
        -- 注意：active list 残留由 try-pop-next-job 的幽灵清理处理
      else
        -- 任务存在，执行原有的恢复逻辑
        local jobKey = ns .. ":job:" .. jobId
        local h = redis.call("HMGET", jobKey, "groupId", "stalledCount", "maxAttempts", "attempts", "status", "score", "delayUntil", "parentId")
        -- ... 原有逻辑代码保持不变 ...
        local groupId = h[1]

        if groupId then
           -- (此处保留原有的恢复/失败判断代码块)
           -- ...
           local stalledCount = tonumber(h[2]) or 0
           local maxAttempts = tonumber(h[3]) or 3
           local attempts = tonumber(h[4]) or 0
           local status = h[5]
           local score = tonumber(h[6])
           local delayUntil = tonumber(h[7] or "0")
           local parentId = h[8]

           if status == "processing" then
              -- ... 具体的恢复逻辑 ...
              -- (代码过长省略，保持原文件内容)
              -- 这里需要将原文件中 if groupId then ... end 的内容完整放这里
              stalledCount = stalledCount + 1
              attempts = attempts + 1
              redis.call("HSET", jobKey, "stalledCount", stalledCount, "attempts", attempts)

              -- 从活跃列表移除
              local groupActiveKey = ns .. ":g:" .. groupId .. ":active"
              redis.call("LREM", groupActiveKey, 1, jobId)

              local shouldFail = false
              local failReason = ""

              if stalledCount >= maxStalledCount and maxStalledCount > 0 then
                shouldFail = true
                failReason = "Job stalled " .. stalledCount .. " times (max: " .. maxStalledCount .. ")"
              elseif attempts > maxAttempts then
                shouldFail = true
                failReason = "Job exceeded max attempts (" .. attempts .. "/" .. maxAttempts .. ") due to stalls"
              end

              if shouldFail then
                -- Fail logic
                redis.call("ZREM", processingKey, jobId)
                local groupKey = ns .. ":g:" .. groupId
                redis.call("ZREM", groupKey, jobId)
                redis.call("DEL", ns .. ":processing:" .. jobId)
                releaseLock({ ns = ns, jobId = jobId })
                redis.call("HSET", jobKey, "status", "failed", "finishedOn", now, "failedReason", failReason)
                
                if parentId then
                  updateParentFlow({
                    ns = ns,
                    parentId = parentId,
                    childId = jobId,
                    status = "failed",
                    resultOrError = cjson.encode({ message = failReason, name = "StalledError" }),
                    timestamp = now,
                    readyKey = readyKey,
                    limitedKey = limitedKey
                  })
                end
                
                redis.call("ZADD", ns .. ":failed", now, jobId)
                table.insert(results, jobId)
                table.insert(results, groupId)
                table.insert(results, "failed")
              else
                -- Recover logic
                local stillInProcessing = redis.call("ZSCORE", processingKey, jobId)
                if stillInProcessing then
                  redis.call("ZREM", processingKey, jobId)
                  redis.call("DEL", ns .. ":processing:" .. jobId)
                  releaseLock({ ns = ns, jobId = jobId })

                  local groupKey = ns .. ":g:" .. groupId

                  if delayUntil > 0 and delayUntil > now then
                    redis.call("ZADD", ns .. ":delayed", delayUntil, jobId)
                    redis.call("HSET", jobKey, "status", "delayed")
                    -- 更新群组状态
                    updateGroupReadyLimitedState({ ns = ns, groupId = groupId, readyKey = readyKey, limitedKey = limitedKey })
                    table.insert(results, jobId)
                    table.insert(results, groupId)
                    table.insert(results, "delayed")
                  elseif score then
                    redis.call("ZADD", groupKey, score, jobId)
                    redis.call("HSET", jobKey, "status", "waiting")
                    updateGroupReadyLimitedState({ ns = ns, groupId = groupId, readyKey = readyKey, limitedKey = limitedKey })
                    redis.call("SADD", groupsKey, groupId)
                    table.insert(results, jobId)
                    table.insert(results, groupId)
                    table.insert(results, "recovered")
                  end
                end
              end
           end
        end
      end
    end
  end

  return results
end
```

### 步骤 3：在核心脚本中集成群组自愈

#### 3.1 修改 `lua/includes/group-lifecycle/update-group-ready-limited-state.lua`

**修改点**：使用通用模块检查群组是否存在，防止 Worker 在不存在的群组上空转。

```lua
--- @include "includes/concurrency-control/is-group-at-capacity"
--- @include "includes/common/validate-group-integrity"

-- 入参:
--   opts.ns: 命名空间
--   opts.groupId: 群组ID
--   opts.readyKey: ready集合key
--   opts.limitedKey: limited集合key
--   opts.headScore: 可选，群组头任务的score；如果不提供，会从群组中获取
-- 功能: 根据活跃计数和并发限制，自动将组置于 ready 或 limited 队列

local function updateGroupReadyLimitedState(opts)
  local ns = opts.ns
  local groupId = opts.groupId
  local readyKey = opts.readyKey
  local limitedKey = opts.limitedKey
  local headScore = opts.headScore

  if not headScore then
    -- [FIX] 使用通用模块检查群组完整性并获取 Score
    headScore = validateGroupIntegrity({
      ns = ns,
      groupId = groupId,
      readyKey = readyKey,
      limitedKey = limitedKey
    })
    
    -- 如果返回 nil，说明群组已空或被删，且已被 validateGroupIntegrity 清理
    if not headScore then
      return
    end
  end

  if isGroupAtCapacity({ ns = ns, groupId = groupId }) then
    redis.call("ZREM", readyKey, groupId)
    redis.call("ZADD", limitedKey, headScore, groupId)
  else
    redis.call("ZREM", limitedKey, groupId)
    redis.call("ZADD", readyKey, headScore, groupId)
  end
end
```
