# PRD: GroupMQ Worker 错误处理与状态流转重构

## 文档目的
重构 `Worker` 类的 `handleJobFailure` 方法，修正 `failed` 事件触发时机滞后于状态变更的问题。确保消费者在监听 `failed` 事件时，能够通过 `job.status` 属性直接、准确地判断任务是“即将重试（delayed/waiting）”还是“最终失败（failed）”。

---

## 任务一：重构 handleJobFailure 状态流转逻辑

### 1. 问题定义
**当前行为**：
在 `handleJobFailure` 方法中，代码首先触发 `failed` 事件，并硬编码传递 `status: 'failed'`。随后代码才进行逻辑判断（检查重试次数、不可恢复错误）并调用 Redis 更新状态。
**后果**：
1.  监听器的 `job.status` 永远为 `'failed'`，无法区分临时失败和最终失败。
2.  消费者被迫使用 `attemptsMade >= maxAttempts` 等不可靠的计算方式来推测最终状态。
3.  事件触发时，Redis 中的数据可能尚未更新，导致此时查询 Redis 得到的状态可能与预期不符。

### 2. 潜在风险
*   **业务逻辑错误**：消费者可能在任务仅是临时失败时误判为最终失败，触发错误的报警或清理逻辑。
*   **状态不一致**：事件携带的状态与 Redis 真实状态存在时间窗口上的不一致，影响监控系统的准确性。

### 3. 修复策略
采用 **"Action First, Event Later"** 策略：
1.  首先执行所有的决策逻辑（计算重试次数、判断错误类型）。
2.  执行 Redis 操作（调用 `retry` 或 `deadLetter`）。
3.  根据 Redis 操作的**实际结果**确定最终状态（`failed` / `delayed` / `waiting`）。
4.  最后触发 `failed` 事件，携带真实的状态值。

### 4. 技术实施细节（核心部分）

#### 涉及文件/模块
*   `src/worker.ts`
*   类：`_Worker`
*   方法：`handleJobFailure`

#### 逻辑变更点
请完全重写 `handleJobFailure` 方法，遵循以下伪代码逻辑：

```typescript
private async handleJobFailure(err: unknown, job: ReservedJob<T>, jobStartWallTime: number): Promise<void> {
  const errObj = err instanceof Error ? err : new Error(String(err));
  const nextAttempt = job.attempts + 1;
  
  // 1. 判定是否为“不可恢复”或“次数耗尽”
  const isUnrecoverable = err instanceof UnrecoverableError;
  const isRetriesExhausted = nextAttempt >= this.maxAttempts;

  let finalStatus: 'failed' | 'delayed' | 'waiting' = 'failed';

  // 2. 分支处理
  if (isUnrecoverable || isRetriesExhausted) {
    // [路径 A: 最终失败]
    finalStatus = 'failed';
    
    // 决定尝试次数记录：如果是次数耗尽，记录 maxAttempts；如果是不可恢复错误，记录当前尝试次数(或 maxAttempts，视现有逻辑而定)
    // 建议保持现有逻辑一致性：如果是耗尽，传 job.maxAttempts
    await this.deadLetterJob(
      err, 
      job, 
      jobStartWallTime, 
      Date.now(), 
      isRetriesExhausted ? job.maxAttempts : nextAttempt
    );
    
    if (isUnrecoverable) {
      this.logger.info(`Unrecoverable error for job ${job.id}. Skipping retries.`);
    }
  } else {
    // [路径 B: 尝试重试]
    const backoffMs = this.backoff(nextAttempt, err);
    
    // 预判状态：有退避时间则是 delayed，否则是 waiting
    finalStatus = backoffMs > 0 ? 'delayed' : 'waiting';

    // 执行重试操作
    const retryResult = await this.q.retry({ id: job.id, token: job.token }, backoffMs);

    // [边缘情况处理]
    if (retryResult === -1) {
      // Redis 返回 -1 表示服务端记录的次数也耗尽了 (Double Check)
      finalStatus = 'failed';
      await this.deadLetterJob(err, job, jobStartWallTime, Date.now(), job.maxAttempts);
    } else if (retryResult === -2) {
      // Redis 返回 -2 表示锁丢失/Token不匹配，任务已被接管
      this.logger.warn(`Lock lost for job ${job.id}: cannot retry`);
      return; // 直接退出，不发送 failed 事件，因为此时 Worker 已失去所有权
    } else {
      // 重试成功入队，记录本次失败尝试信息
      await this.recordFailureAttempt(err, job, jobStartWallTime, Date.now(), nextAttempt);
    }
  }

  // 3. 构造并触发事件 (此时 finalStatus 已是最终确定的状态)
  
  // 触发 onError (保持原有逻辑，用于日志记录等)
  const jobForError = Job.fromReserved(this.q, job, {
    processedOn: jobStartWallTime,
    status: 'active' 
  });
  this.onError?.(err, jobForError);

  // 触发 'failed' 事件
  this.emit(
    'failed',
    Job.fromReserved(this.q, job, {
      processedOn: jobStartWallTime,
      finishedOn: Date.now(),
      failedReason: errObj.message,
      stacktrace: errObj.stack,
      status: finalStatus, // <--- 核心修改：传入真实状态
    })
  );

  // 触发 'error' 事件 (保持原有逻辑)
  try {
    this.emit('error', errObj);
  } catch (_emitError) { }
}
```

### 5. 交付标准

AI 在完成代码修改后，代码行为应满足以下断言：

1.  **临时失败测试**：
    *   当任务失败且 `attempts < maxAttempts` 时：
    *   `failed` 事件必须触发。
    *   事件回调中 `job.status` 必须为 `'delayed'` (如果配置了 backoff) 或 `'waiting'`。
    *   Redis 中该任务不应存在于 `failed` 集合中。

2.  **最终失败测试**：
    *   当任务失败且 `attempts >= maxAttempts` 时：
    *   `failed` 事件必须触发。
    *   事件回调中 `job.status` 必须为 `'failed'`。
    *   Redis 中该任务应存在于 `failed` 集合中。

3.  **不可恢复错误测试**：
    *   当抛出 `UnrecoverableError` 时（即使 `attempts < maxAttempts`）：
    *   事件回调中 `job.status` 必须为 `'failed'`。

4.  **锁丢失测试**：
    *   如果 `q.retry` 返回 -2，不应触发 `failed` 事件。

### 6. 全局视角
*   确保 `Job.fromReserved` 方法能够正确接收并处理传入的 `status` 参数（根据现有 `job.ts` 代码，这是支持的）。
*   保持 `this.emit('error', ...)` 的行为不变，以维持对现有错误监控系统的兼容性。
